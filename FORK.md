# Maintaining this fork

Personal fork of OpenIDEA (`audichuang/openidea`, remote `fork`; upstream `l0ng-ai/openidea`, remote `origin`). Fork-only code lives in fork-owned files where possible; upstream files carry the smallest diff that wires it in. Read this before rebasing, before merging fork work into `develop`, and before releasing. `AGENTS.md`, `CLAUDE.md`, `.agents/` and `.claude/` are fork-owned since upstream removed them in `fd959cc87` (v0.1.52): no upstream copy to follow or conflict with.

## Terms

- **Fork base**: the newest upstream GitHub Release tag (`vX.Y.Z`) that `develop` sits on. A tag upstream pushed without publishing a Release does not count.
- **develop**: the fork's integration branch: fork base plus the fork's commits. The GitHub default branch.
- **main**: a pointer to the last released commit. It only ever moves by force-push at release time.
- **Rebase lock**: a `rebase/vX.Y.Z` branch on the fork. While it exists an automated rebase is in flight or waits for the user.
- **CLEAN**: a rebase with no conflict and no extra commit.
- **MECHANICAL**: a rebase whose only conflicts are the mechanical kinds in "Rebase conflicts" (resolved by `scripts/fork/resolve-conflicts.py` or by regenerating a file), plus at most the regenerate commit.
- **MANUAL**: any other rebase: a conflict resolved by judgement, a fix commit, a dropped commit.

## Red lines

- Push only to `fork`, never to `origin`. Upstream PRs only from `up/*` branches under the `openidea-upstream-pr` skill; security problems go to upstream's private advisory, never a public PR.
- Every change, docs included, goes on a branch with a PR into `develop`, merged with a merge commit once Fork CI is green (`gh pr merge <n> --merge`; who may merge: `AGENTS.md`). Auto-merge is off, so `--auto` fails: wait with `gh-wait pr <n> -R audichuang/openidea`, then merge. A red the agent cannot fix, or a call it cannot make, leaves the PR open for the user. The auto-rebase's own `develop` and release pushes follow its skill.
- Nobody pushes `develop` directly except a rebase: the auto-rebase's lease push, or the user's own verified rebase. `develop` and `main` have no branch protection on purpose, since rebases force-push them.
- A branch cut from `develop` before a rebase moved it: `git rebase --onto fork/develop <its old merge-base>`. A plain rebase replays the old upstream range along with it.

## Platform scope

- Fork features must work on macOS, Windows and Linux, and a ClipCode payload copied on one OS must paste correctly on another (the user copies on the Mac and pastes on a Windows machine, and back). Paths inside a payload are always `/`-spelled; each OS converts at the edge. `crates/ide-clip/fixtures/clipboard-contract.json` is the shared contract and passes in the macOS, Linux and Windows test jobs.
- The ClipCode format is shared with the IntelliJ, VS Code and Orca implementations. A fix that would change the format is a four-repo change: stop and take it to the user, never change it here alone.
- Copying non-text files (images, archives, Big5) as Base64 follows `docs/clipcode/non-text-files.md` in all four implementations.
- Releases ship the macOS arm64 app and the Windows x64 installer.

## Merge gate

- Fork CI (`.github/workflows/fork-ci.yml`) is the gate; its `Fork CI passed` job is the one result to read. It runs on PRs into `develop` (the only run anyone waits for), again on the merge's `develop` push (caches, and two PRs that pass alone but not together) and on `rebase/**` pushes. What each job does and why is in the workflow's and its actions' comments. A newer push replaces a `develop` run still queued, so after merging a batch judge the last `develop` run.
- A red job gets one `gh run rerun <id> --failed`; red again is real. A rerun reruns the same commit: a PR red only on a test another PR fixes turns green once that fix is merged and the PR is rebased and pushed. Hosted macOS arm64 runners are scarce: a macOS job queued for long or cancelled with "The job was not acquired by Runner" is capacity, not the change: rerun it, and cancel superseded runs (`gh run cancel`) to free runners. The repo's cache limit is 30 GB.
- A red that upstream's own CI shares does not count as green. Port upstream's fix when `origin/main` has one, otherwise fix the test or filter it by full name with a tracking issue as for #252. A test that flakes again gets an issue and a fix, not more reruns: prove the cause by injecting a delay that makes it fail every time, then wait for an explicit condition with a deadline, not a longer sleep or a retry (#298 → #301, #309–#316). An E2E that fails only in Fork CI reproduces in the workflow's Playwright `container:` image on the ubuntu host with `--cpus 2`: the Mac's fallback font is nearly as wide as JetBrains Mono, so layout races around the web font load show only on Linux (#457).
- Upstream's `ci.yml` stays unedited. The `upstream-ci` job pins its SHA-256 and fails when a rebase brings a changed `ci.yml`: port the change into `fork-ci.yml`, then update the pin.
- Locally before pushing: the checks in `AGENTS.md`. The `ubuntu-remote` nextest profile leaves out the tests `.config/nextest.toml` lists for host reasons, but other tests fail on that host on upstream too (for example `ide-search`'s `bounded_memory`): check a failure on the fork base on the same host before calling it the change's. If an older `rust-remote` lacks its `git ls-files` second pass, the plugin tests fail with `dist/plugin.wasm is missing` and `ide-ssh` with `E0583: file not found for module remote_url`; send those files by hand: `git ls-files -co --exclude-standard | rsync -az --files-from=- ./ ubuntu:build/$(basename "$PWD")/`.
- Only `Fork CI` and `Fork Release` stay enabled. Upstream's workflows are disabled with `gh workflow disable`, including one a rebase brings, right after `develop` moves (`pull_request_target` runs the workflow from the PR's base branch, so it fires on the next PR into `develop`); a fork experiment's workflow is disabled when the experiment ends. Check with `gh workflow list -R audichuang/openidea`, which lists the enabled ones.

## Rebase conflicts

Rebase with `git rebase --onto <vNEW> $(git merge-base fork/develop origin/main)`: `develop` may sit on upstream commits past its release tag. Keep `git config rerere.enabled true`. A fix to one earlier fork commit is committed with `git commit --fixup=<that commit>` when its subject is unique in the fork range; before replaying, fold them on the old base with `git -c rerere.enabled=false rebase --autosquash $(git merge-base fork/develop origin/main)` and keep the result only if `git diff <old develop> HEAD` is empty (details: auto-rebase skill step 1). During a rebase "ours" is the new upstream side and "theirs" the fork commit.

Mechanical kinds (`scripts/fork/resolve-conflicts.py` is the fork's own file, absent until its commit replays: run it from `fork/develop`, `git show fork/develop:scripts/fork/resolve-conflicts.py > /tmp/resolve-conflicts.py`):

- **Locale JSON** (`src/platform/locales/**`): `python3 scripts/fork/resolve-conflicts.py locale <file>` keeps upstream's side and adds the keys the fork adds, dropping keys upstream removed. A key upstream also added with the identical string, anywhere in the file, keeps only upstream's copy. It refuses when the fork changes or removes an upstream key, upstream has a key the fork adds with a different string, or the merge adds a duplicate key (a key upstream's own file already repeats, as v0.1.40's `zh.json` does, is left alone). On v0.1.47 the same keys (l0ng-ai/openidea#3765 and a fork commit) merged without a conflict at different spots, so the resolver never ran and the duplicate needed `fix(fork): 拿掉和上游重複的 Related Symbol／Extract Interface 選單文字`: after a rebase, a clean merge can still duplicate a locale key, and the i18n and `textCatalog` tests catch it.
- **Appended tests**: both sides added tests at the end of the same file. `python3 scripts/fork/resolve-conflicts.py append <file>` keeps both, upstream first; it refuses when any hunk edits existing lines.
- **Imports**: both sides edited the same block of one-line `import`/`use` statements, such as an import added next to one the other side changed (v0.1.45's `WindowGroupTabs.tsx` and `commitChecks.tsx`, v0.1.47's `history.rs` and `ops.ts`). `python3 scripts/fork/resolve-conflicts.py imports <file>` applies both sides' line edits to the base, upstream's insertions first. It refuses a line in a conflict hunk that is not a whole one-line import (multi-line lists such as v0.1.47's `pub use runtime::{…}`, comments, code), a base line both sides edit differently, and a name the merge imports twice.
- **Generated files** (`Cargo.lock`, `pnpm-lock.yaml`, `src/bindings.ts`): take upstream's side, then regenerate once the rebase ends (`pnpm install --lockfile-only`; `rust-remote --pull Cargo.lock metadata --format-version 1`; `src/bindings.ts` too, in the same regenerate commit: taking upstream's side drops every fork command the conflicting commit had, as on v0.1.40). A fork crate's version follows the workspace version, so `Cargo.lock` changes on every upstream version bump.

Anything else is MANUAL: keep the fork's behaviour, adopt upstream's new structure.

## Reserved for the user

The unattended rebase reviews MANUAL resolutions itself (below), except when a hand-resolved conflict or a fix commit touches these paths. They need the real app on the user's screens or a decision outside this repo, so the lock waits for the user. Window chrome (the first item) is the exception: the run builds the dev app on the Mac mini and checks it there itself (the skill's step 3c, following `fork-verify`'s `features/window-tabs.md`), and hands back only when a check fails or cannot run, or when another path below is hit too (it still checks chrome first):

- macOS window chrome and project window groups: `src-tauri/src/{macos,window_groups,titlebar}.rs`, `src/workbench/WindowGroupTabs.*`, `src/workbench/TitleBar.*` (the real fullscreen Space check above; AppKit chrome is invisible to every automated test). Step 3c does not cover the menu bar shown in fullscreen (a global `defaults` change), notched displays or tab drags.
- The ClipCode format: `crates/ide-clip/**`, `docs/clipcode/**` (a four-repo contract, "Platform scope").
- The update chain: `src-tauri/src/fork_updater.rs`, `.github/workflows/fork-release.yml`, `.github/actions/fork-release-setup/**` (a broken updater cannot fix itself on the user's three machines).
- Anything that weakens the gate: a fix commit that changes `.config/nextest.toml`, adds a test filter or skip to `fork-ci.yml`, deletes, ignores or skips a test, adds an inline suppression, a baseline or allowlist entry, or loosens an existing assertion (a green CI the fix itself produced proves nothing). Exceptions: the auto-rebase skill's step 3b.

Upstream's own changes to the window-chrome paths count too, in every mode (CLEAN and MECHANICAL included), conflict or not, renames by their old and new paths; so does a dropped fork commit that touched any of these paths.

## Unattended rebase

- The Orca automation "OpenIDEA fork 自動 rebase" fires hourly at :37. Its precheck (`.claude/skills/openidea-fork-auto-rebase/scripts/precheck.sh`, read from `fork/develop`) lets the agent run only when upstream published a newer Release than the fork base, a rebase lock went stale or obsolete, a fork base is still unreleased, or the user approved a needs-human PR (below). The agent follows the `openidea-fork-auto-rebase` skill in a fresh worktree on `fork/develop`: CLEAN, MECHANICAL, and MANUAL that passes its own review outside the paths "Reserved for the user", move `develop` and release; anything else leaves the `rebase/vX` lock and a PR marked needs-human, with a Bark notice either way. How it classifies, reviews and hands back is in the skill.
- To hand a needs-human PR back after review, comment with `<!-- auto-rebase:approved <full sha of the rebase/vX tip> -->` as the first line; the next hourly run moves `develop` and releases without redoing the rebase or the gates. The approval settles only what needed the user, never a red Fork CI or a Release upstream withdrew since (#509). Pushing to `rebase/vX` afterwards voids it, and so does a later needs-human comment: to withdraw an approval, post the needs-human marker yourself.
- While a rebase lock exists, hold merges into `develop`; a merge meanwhile makes the lease fail and the next run starts over. The `.claude/settings.json` hook (`.claude/hooks/rebase-lock-merge-guard.sh`) refuses `gh pr merge` while a `rebase/*` branch is ahead of `develop`; if the user still wants the merge, carry `old-develop..develop --no-merges` onto the lock afterwards (as for v0.1.45) before approving it.
- The skill and its scripts live in `.claude/skills/openidea-fork-auto-rebase/` and change through a PR. Only the automation definition, `BARK_URL` (Doppler `shioaji`/`dev`) and `~/.config/fork-automation/precheck-alert.sh` live on the machine.

## Release

- Version `vX.Y.Z-fork.N`: X.Y.Z is the fork base, N counts up per base from 1.
- Every fork base gets released. Whoever moves `develop` onto a new base (the automation, or a rebase done by hand in a session) tags `vX.Y.Z-fork.1` once the develop push's Fork CI is green, in the same session; the hourly precheck's RELEASE mode is only the backstop. A tag's release run uses the workflow at the tag's commit, so a release that failed on the workflow itself is not rerun: once the fix is on `develop` with green Fork CI, release it as the next `fork.N` and leave the failed tag (#355).
- Wait with an explicit target and `-R audichuang/openidea`: `gh-wait commit <develop sha> -R audichuang/openidea` after moving `develop`, `gh-wait tag vX.Y.Z-fork.N -R audichuang/openidea --workflow fork-release.yml` after the tag push. A bare `gh-wait` in the main checkout waits on its own stale `develop`.
- Move `main` and push an annotated tag in one atomic push. The tag message is the release notes, in Traditional Chinese: the fork base, upstream's user-visible changes since the last release, the fork's user-visible changes. After rewriting fork history (a filter that moves the `vX.Y.Z-fork.N` tags), move `main` to the rewritten commit of the newest tag as well; on 2026-11-22 the tags moved and `main` stayed on the previous release.

  ```sh
  old=$(git ls-remote fork refs/heads/main | cut -f1)
  git tag -a vX.Y.Z-fork.N <sha> -F notes.md && git push --atomic --force-with-lease=main:$old fork <sha>:refs/heads/main vX.Y.Z-fork.N
  ```

- The tag push runs `.github/workflows/fork-release.yml` (what it checks, builds and publishes: its comments). Both platforms must succeed before it publishes: a Windows failure blocks the release like a macOS one, since both are in daily use. Re-running it on the same tag replaces the assets and notes. The updater signing key and its password are in 1Password (Agent vault). Windows ships NSIS only (MSI rejects a pre-release version) without an Authenticode signature, so a browser-downloaded installer meets SmartScreen once; the app's own updates do not.
- Every `develop` push builds a release candidate that a matching tag publishes without rebuilding, and a newer push cancels the candidate in flight: merge a batch of PRs back to back. Candidate and tag builds share `.github/actions/fork-release-setup`, so a `CARGO_*` variable added to only one side breaks the cache. Judge a build-speed change by the unit durations in the `cargo-timings-*` artifacts (the HTML's `UNIT_DATA` array), not the job's wall time (the same unit varies about 2× between hosted runners). To try a workflow change without releasing, push a `fork-release-dryrun-<anything>` tag, and delete it afterwards.
- Installing: macOS `brew install --cask audichuang/tap/openidea-fork` once; the cask says `auto_updates true`, so later updates come from the app and `brew upgrade` leaves it alone. Windows: run `openidea-fork-windows-x64-setup.exe` from the release once; it replaces an official OpenIDEA install and shares its settings, like the Mac build.
- Pushed tags and `backup/*` branches keep released commits reachable after a rebase rewrites `develop`.
